## Operational encrypted aggregate

The live execution engine's operational persistence uses `changerelay_private.runtime_state`: one encrypted aggregate per primary owner workspace, with a monotonic database revision. This retains exact engine plan hashes, immutable snapshots, latest-plan pointers, runs, step checkpoints and fenced leases without exposing provider identifiers in public tables. The public normalized records are an optional reporting/design model; the aggregate RPCs do not automatically populate them. Choose **one execution mechanism** for a live event. Do not run the normalized queue RPCs and aggregate-engine workers independently over the same event.

Only `service_role` can execute these `SECURITY INVOKER` RPCs:

- `ensure_runtime_workspace(p_owner_id uuid, p_name text default 'ChangeRelay workspace')` returns the same primary workspace on repeated calls. A partial unique index enforces one primary workspace per owner. Clients cannot set its server-only primary marker.
- `read_runtime_state(p_owner_id uuid, p_workspace_id uuid)` returns `revision`, encrypted `ciphertext` (`bytea`), `key_version`, `updated_at` and fresh `server_time` from the database clock; no row means no aggregate has yet been created. A foreign/deleting workspace is rejected.
- `compare_and_swap_runtime_state(p_owner_id uuid, p_workspace_id uuid, p_expected_revision bigint, p_ciphertext bytea, p_key_version text)` inserts revision 1 only for expected revision 0, or replaces a matching revision and increments it. It returns `false` for a stale revision and never overwrites it. Payloads are limited to 2 MiB. The parent workspace is locked briefly to coordinate CAS and deletion; no provider request occurs in that transaction.

The backend derives `p_owner_id` from verified Auth, reads/decrypts the aggregate, applies deterministic engine validation and state transitions, encrypts the replacement using a server-only purpose-separated key, then CAS-writes against the revision it read. A stale CAS requires re-read and re-evaluation; do not blindly overwrite. Prefer the returned database time when evaluating lease expiry. Envelope encryption must use a fresh nonce, authenticated encryption and an owner/workspace-bound context; never return the plaintext aggregate, key or ciphertext to a browser. PostgREST represents `bytea` as a `\\x`-prefixed hex string. The local PGlite validator binds actual byte buffers instead, because its SQL parameter encoder differs from PostgREST.

CAS supplies atomic storage and owner isolation. The engine remains responsible for approving only the latest exact plan, one unfinished run per event, durable step checkpoints, unique receipts, finite leases, stale-source checks and uncertain-send recovery. A database revision alone does not prove those application invariants or a real provider update. Keep their engine tests alongside the database checks.

## Data and access model

The first release uses one authenticated owner per workspace. There are no team-sharing policies yet. Every child row repeats `owner_id` and `workspace_id`, and composite foreign keys require its parent to belong to that exact owner and workspace. A forged owner or a cross-workspace event/connection/participant ID cannot form a valid relationship. Owners cannot update these identity columns through client grants.

Every public table has RLS and an explicit owner-scoped SELECT policy that also checks its real parent workspace. `anon` has no grants. Only workspace preferences, roster entries, volunteer assignments and unlocked change-request drafts have limited authenticated INSERT/UPDATE grants and matching owner policies. UPDATE includes both `USING` and `WITH CHECK`, plus a SELECT policy. User-editable JWT `user_metadata` is not used for authorisation.

Connection and event-link summaries expose friendly labels and readiness only. The non-exposed `changerelay_private` schema holds encrypted viaSocket credential/reference records and worker leases. It has no PUBLIC/anon/authenticated schema, table or function privileges. Keep it out of the project's Data API exposed schemas. A server-held KMS/application key must encrypt the credential JSON; do not keep that encryption key in this database. The application should continue letting viaSocket hold Google OAuth tokens.

Events, confirmed mappings, plan versions, approvals, runs, steps, delivery outcomes and audit entries are server-written, owner-readable. Client requests to connect, link, approve, retry, disconnect or remove data go through authenticated backend operations. The backend validates the identity, current session, parent ownership and actual provider records; a browser cannot mark its connection verified, forge an approval, change worker state or declare a provider operation successful.

`plan_versions.snapshot` contains the exact schedule, message, recipients, conflict acknowledgements to be requested, semantic action list and source fingerprints. The INSERT trigger computes the SHA-256 hash from PostgreSQL's JSONB text representation and rejects every UPDATE. The backend must read this returned database hash and bind approval to it; it must not assume its own JSON serialiser produces the same bytes. An edited proposal creates a new immutable version and needs approval again. Approval rows cannot be client-written or service-role-updated. Their hash is constrained to the exact referenced plan. Credential/provider IDs must not be embedded in public snapshots.

## Durable execution contract

1. On approval, the backend re-reads the selected Calendar and Sheet records, checks fingerprints and the event version, then creates the approval, run, all planned steps and per-recipient receipt rows in one transaction. Every query includes the authenticated `owner_id`, even when the database client uses a secret/service-role key. Never obtain an owner filter from an unchecked request body. Unique approval and unfinished-event constraints reject duplicate or overlapping runs.
2. A scheduled worker calls the service-role-only `claim_execution_run(owner, worker, lease_seconds)` RPC. `FOR UPDATE SKIP LOCKED` selects one due run, and a private lease provides one current worker per event. Leases are finite (15–120 seconds), have an unguessable token and fencing generation, and survive page closure. The worker must persist/renew its lease and stop when renewal fails.
3. Before each external action, confirm the lease is still valid and the approved source state still matches. Mark the step running using the fenced checkpoint RPC, then make the awaited viaSocket SDK call with a timeout shorter than the remaining lease. Do not start another operation if the lease is lost. Never make provider HTTP calls inside a database transaction.
4. Save and read back Calendar and Sheets separately. Only then record `verified` with safe verification evidence. Completed steps are immutable through the checkpoint RPC. Preceding steps must finish before a later one starts; required Calendar/Sheet steps cannot be skipped. A JSON object alone does not prove external verification—the worker must check actual returned values before supplying it.
5. Send approved announcements individually only after required schedule steps verify. `notification_outcomes` has `unique(owner_id, receipt_id)` and `unique(owner_id, run_id, participant_id)`; persist these receipts before dispatch. Record an accepted send separately from an acknowledgement. Provider identifiers stay encrypted in the private provider-record table. Future acknowledgement links require separate random, scoped, expiring tokens and a minimal public response; this draft does not implement them.
6. Reclaiming an expired lease pauses running steps and dispatching notifications as `needs_checking`; it does not replay an in-flight call. Reconcile current source values or the provider's message result first. A timeout does not prove a send failed. If the provider cannot establish the result, keep it uncertain and require organiser attention; do not blindly resend. Database fencing cannot cancel an already-running external provider request, so this system cannot promise exactly-once external delivery or cross-app atomicity.
7. `release_execution_run` derives the resulting state from all saved steps and uncertain sends, then releases the lease. Failed/needs-checking runs block new runs for the same event. A reviewed retry must reconcile source fingerprints, retain verified steps and the original approved snapshot, then explicitly return only safe failed/pending work to the queue. Unreviewed `needs_checking` work is never auto-queued. An actual reversal is a new reviewed plan; sent mail cannot be undone.

SQL alone does not implement the worker schedule, provider adapters, application approval/retry checks, authenticated routes, encryption, rate limits or account-removal orchestration; the application engine/store supplies those behaviours. The service role intentionally has operational table rights, so any backend using the optional normalized queue must consistently use its fenced RPCs rather than bypassing them with broad direct updates. The operational encrypted aggregate instead uses its engine invariants and atomic CAS. A later hardening pass may replace broad server writes with narrower transaction RPC grants once the reporting routes are defined. pgTAP is still outstanding.

## Disconnection and removal

Disconnecting an app first pauses dependent jobs, lets active leases expire or reconciles their in-flight operations, then revokes the viaSocket connection and removes its private credential/reference records. Removing a local reference alone does not revoke the provider connection. Preserve an honest, non-secret audit summary of what happened.

Workspace deletion is an authenticated server operation: validate owner/session, set `deletion_requested_at` (hides client child rows and blocks new claims/renewals), stop and reconcile workers, revoke the relevant viaSocket connections, then delete the owner's workspace row. Cascades remove that workspace's event, roster, approval, execution, outcome, private-reference and audit records. Define the desired export/retention policy before enabling this operation; do not retain personal content indefinitely by accident. Verify the restrictive parent/child deletion interactions in PostgreSQL before launch.

Account deletion is separate from logging out. Revoke/sign out Supabase sessions first, verify current sensitive operations against the session where strict invalidation is required, finish workspace cleanup, then delete the Auth user. A user deletion alone does not invalidate an already-issued access token. The `auth.users` foreign key is restrictive to avoid silently deleting active work during an accidental Auth-user removal. Signing out alone must not erase event data.

## Migration history and remaining verification

The initial source snapshot was applied through the selected project's SQL editor because the connector tools were unavailable. Do not rerun its CREATE statements or label this file an applied CLI migration. Establish migration history before further production schema changes: use the CLI's `--help` to discover installed commands, confirm its version, inspect the actual remote schema, choose a development project and review current documentation. The Supabase skill requires schema iteration through `execute_sql` or `supabase db query`, advisors before commit, and CLI-generated migration history. Use `supabase migration new <name>` when creating a new migration file; never invent a timestamped filename. When generating a clean migration from verified local work, follow the installed skill's `db pull ... --local` workflow and verify the migration list.

Extend the existing local/live checks into policy tests using the CLI's test command and run `supabase test db`. Required cases include:

- Every public table has RLS; anon has no read/write privileges; authenticated cannot reach private credentials, leases or management RPCs.
- Owner SELECT/INSERT/UPDATE succeeds only where intended, with actual returned row values. Non-owner reads are empty, writes cannot change the target, and foreign-owner/workspace IDs are rejected.
- Identity columns, connection readiness, confirmed mappings, plan snapshots/hashes, approvals, run status, step status and audit records cannot be written by ordinary clients.
- Parent workspace reassignment cannot create a forged owner relationship; a deleting workspace is invisible to child policies and unclaimable.
- Concurrent approvals yield one run; concurrent claims yield one lease; another worker cannot checkpoint with an old token/generation; expired or NULL leases are rejected.
- A worker restart retains verified steps, claim pauses an uncertain in-flight send, no duplicate receipt is inserted, and stale fingerprints block retry.
- Hash calculation and immutable-plan trigger behave correctly on the actual PostgreSQL version.
- Deleting a workspace removes only that owner's records, preserves other owners, handles restrictive references correctly, and does not merely sign out the user.

## Local PostgreSQL-engine validation

PGlite 0.5.13 is an exact development dependency in the app's package lock. From the ChangeRelay project directory, reproduce with:

```text
npm ci
npm run test:database
```

The validator uses a normal package import and needs no files from the task's temporary work directory. It creates a completely separate, in-memory PostgreSQL-compatible database with minimal stub `auth.users`, `auth.uid()` and standard Supabase roles. It applies the complete SQL, then exercises all 18 tables' RLS declarations, eight invoker functions, owner visibility, anon/client denials, composite-parent constraints, limited column grants, immutable plan/hash behaviour, unique runs, lease fencing and expiration, ordered checkpoints, receipt constraints, private runtime CAS and cascading deletion. Sixteen named runtime checks pass. No configured Supabase URL or key is read.

Two simultaneous JavaScript CAS submissions using the same expected revision yield exactly one winner locally. PGlite schedules a single database connection, so that local check verifies atomic stale-write semantics rather than true independent-session lock contention. The separate live suite also sent independent concurrent HTTP CAS requests to the actual Supabase project: exactly one succeeded and the stored revision was 2. Real Auth sign-in/getUser, cross-owner RLS, forged-write denials and anon/authenticated management-RPC denials also passed live. Genuine multi-session normalized-queue `SKIP LOCKED`, concurrent lease expiry/renewal, pgTAP and full advisors still need checking. These database results do not establish that every live Google integration action has been verified.
